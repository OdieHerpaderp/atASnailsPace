meshes/faces/….glb

Thirteen faces, one file each, all built in head-local space: the origin is the centre of a snail's head, +x forward out of the face, +y up, and ±z either side. That is the frame headG is at in meshes/snail.glb, so a face drops onto it at the origin with no offset table — which is the only reason there is no table to keep in step.

**Every part is laid on the head, not in front of it.** The head is an ellipsoid of radius 0.112 scaled 1.00, 0.97, 1.02, and a brow placed at the eye's own x floats a centimetre off the side of the face at its outer end and touches it in the middle, which at race distance reads as a smudge. So onHead() builds each piece where it wants to be and then pushes it onto the ellipsoid, keeping its own depth: that is one function and it is the whole of how ten faces sit on one head.

The eyes are the exception and are the file's own numbers — (0.088, -0.018, ±0.054) at radius 0.033, which is where snail.glb already puts eyeM. A face drawn anywhere else would not cover the eyes it is standing in front of.

One file is one mesh named face-<name>, holding the whole face: eyes, brows and mouth together, because a face is swapped as a face and three meshes is three draw calls and a join to see. Everything is merged flat, carries a vertex colour, and has no uv at all — a face is four centimetres across, so the maps are the colour in the vertices and there is nothing a tiling map could add. meshes/maps.js says so with an empty array per face, which is the same state an unconverted prop is in.

Open this page from the folder that serves the game and press a button, and the file is written into meshes/faces/ over the one of the same name; nothing is downloaded and nothing has to be moved. The colour is out of the county's own jar (meshes/palette.js) and not invented here.
